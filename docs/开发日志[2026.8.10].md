## Plan / 策划

### 背景与目标

当前项目 v1.2.0 已完成数据全面落库（Todo / Note / MusicTrack / Task / TaskLink），是一个标准的 Next.js 全栈 Web 应用：App Router + Server Actions + Prisma + SQLite + 多用户账号体系。用户提出将其发展为桌面软件，本日志只做策划，讨论开发方向、技术栈、成本、兼容性与实施路线，不涉及代码改动。

桌面化的核心问题：项目本质是"客户端-服务器"结构，服务端（Server Actions、Prisma、文件上传、认证）依赖 Node 运行时。桌面版需要一个"壳"承载本地服务端与前端界面，并把数据库与上传文件落在本机用户目录。

### 一、方向

#### 1. 现状约束

- 服务端与 UI 同仓：Server Actions 直接操作 Prisma，无法简单剥离为纯静态前端。
- 依赖 Node 运行时：Next.js standalone 服务器、Prisma 查询引擎、sharp 图片处理均为 Node 原生能力。
- 数据为本地 SQLite + 本地上传目录，天然适合单机部署，无需迁移到远程数据库即可桌面化。

#### 2. 候选方案对比

| 方案 | 渲染方式 | 后端承载 | 包体 | 内存 | 开发成本 | 生态成熟度 |
|------|----------|----------|------|------|----------|------------|
| Electron | 自带 Chromium | Node 直连，可直接运行 Next standalone | 约 100-200MB | 较高 | 低（JS/TS 全栈延续） | 极高 |
| Tauri 2 | 系统 WebView | Rust 核心；Node 服务需 sidecar 方式托管 | 约 5-15MB | 低 | 高（需学 Rust + 维护 sidecar） | 中 |
| PWA | 浏览器 | 需外部托管服务端，否则仅离线壳 | 0 | 低 | 低 | 高 |
| Neutralino / Wails | 系统 WebView | 需改造后端接入 | 小 | 低 | 中高 | 低 |

#### 3. 方向决策

推荐 **Electron + Next.js standalone 输出**：Electron 主进程启动本地 Next 服务器（localhost），BrowserWindow 加载该地址，实现"全栈应用本地化"。理由：

- 零后端改造：Server Actions、Prisma、sharp 全部原样复用，不引入 Rust 维护成本。
- 前端零改动：现有 /dashboard 全部页面与组件直接运行。
- 数据完全离线：SQLite 与上传文件移入系统用户目录，符合本地工具定位。
- 生态最成熟：electron-builder、electron-updater 等工具链完善。

Tauri 作为远期备选（若未来追求极致包体与内存），但当前阶段不推荐，原因：本项目服务端是 Node 生态，Tauri 必须用 sidecar 跑 Node，相当于同时维护 Rust 与 Node 两条链路，成本与故障面都更大。

### 二、技术栈

#### 1. 桌面壳

- Electron（主进程 + 渲染进程），渲染进程加载 http://localhost:<port>。
- 端口策略：启动时探测空闲端口（默认 3621），避免与用户其他服务冲突。
- next.config.ts 增加 `output: 'standalone'`，产物自带最小 Node 服务器，随 Electron 一起打包。
- 主进程生命周期：启动本地服务器（等端口就绪）后创建窗口，应用退出时关闭服务器进程。

#### 2. 数据与文件落点

- SQLite：`DATABASE_URL` 由 `file:./dev.db` 改为指向 `app.getPath('userData')/data/dev.db` 的绝对路径，首次启动自动建库并执行 `prisma db push`。
- 上传文件：`public/uploads` 迁移至 `userData/uploads`，上传/预览路径参数化（涉及 `src/actions/files.ts`、`src/actions/music.ts`、`src/lib/wallpaper.ts`）。
- 账号体系：桌面版为单机环境，策划两条路线待定——保留现有登录（多账号本地隔离）或增加"免登录单用户模式"（环境变量跳过认证，直接进入工作台）。

#### 3. 打包与分发

- electron-builder：Windows（NSIS 安装包）、macOS（dmg）、Linux（AppImage）。
- 原生依赖处理：Prisma 查询引擎、sharp 需复制进 asar 外部目录（extraResources）并在运行时指定路径，必要时执行 electron-rebuild。
- 自动更新：electron-updater + 更新服务器（GitHub Releases 即可满足）。

#### 4. 新增依赖清单（策划）

- electron、electron-builder、electron-updater（打包分发）
- @electron/rebuild（原生模块 ABI 重建）
- wait-on 或自实现端口探测（服务器就绪等待）
- 桌面特性库：全局快捷键、托盘（可选用 electron 内置 API 实现，避免额外依赖）

### 三、成本

#### 1. 开发成本

- 壳层开发量小：主进程、本地服务器启动、路径重定向、打包配置，预计一个版本周期（对应 v1.3.0）。
- 主要工作量在数据路径参数化（数据库与上传目录）与桌面特性（托盘、快捷键、自启）。
- 不引入 Rust，无额外语言学习成本。

#### 2. 包体与资源占用

- Electron 安装包约 100-200MB（含 Chromium），运行时内存占用较高，对个人工具可接受。
- 若未来包体敏感，再评估 Tauri 迁移（届时需承担 sidecar 维护成本）。

#### 3. 分发与签名成本

- Windows 无签名也可分发（有 SmartScreen 提示），正式发布建议 Authenticode 证书（约数百元/年）。
- macOS 发布需要 Apple Developer 证书（99 美元/年）并完成 notarization，否则 Gatekeeper 拦截。
- Linux 免费分发（AppImage）。
- 自动更新服务器可复用 GitHub Releases，无额外费用。

### 四、兼容性

#### 1. 系统平台

- Windows 10+：主目标平台，Electron 自带 Chromium，渲染一致性最好。
- macOS 10.15+：需开发者证书签名与公证。
- Linux：AppImage 通用格式，依赖系统 GLibc 版本。

#### 2. 运行时依赖

- 项目需 Node 18+（Next standalone 服务器要求），打包产物内含 Node 运行时，最终用户无需安装 Node。
- sharp、Prisma 为平台原生模块，打包时须匹配 Electron ABI 与目标平台，这是桌面化最主要的兼容性风险点。
- 渲染端不依赖系统 WebView（Electron 自带 Chromium），规避了 Tauri 方案在不同系统上的 WebView 版本差异问题。

#### 3. 数据兼容

- v1.2.0 起数据已全部落库，桌面版沿用同一 SQLite 结构与 Prisma schema，可无缝承接。
- Web 版与桌面版数据可通过复制数据目录迁移（策划阶段暂不做自动迁移工具，列入远期）。

### 风险与瓶颈点（策划预判）

- 原生模块打包（Prisma 引擎、sharp）是最大技术风险，需在 v1.3.0 原型阶段优先验证。
- 免登录单用户模式与现有 Session 认证的取舍，影响后续同步能力的架构。
- Electron 包体与内存开销对"轻量工具"定位的冲击，需在原型阶段实测后再决定是否转向 Tauri。
- 本轮仅策划，未产生代码改动；后续版本落地时按惯例补充 Coding / Target / Questions / Follow 章节。
