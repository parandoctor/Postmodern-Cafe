# 版本更新流程（强制规范）

> 本文件是版本更新工作流的唯一权威入口，来源为 mission.md「开发隔离」规范与 README「贡献指南」。
> 每次版本更新（如 1.2.4 -> 1.2.5）必须完整执行下方清单，**文档与代码必须同批提交**，禁止先推代码后补文档。

---

## 数据安全与分支卫生（强制，最高优先级）

> 用户特意要求，违反视为严重错误。本地独有、未上传的文件（如 mission.md、AGENTS.md、dev.log、.env 等）必须先备份，未经用户特意批准禁止删除任何本地独有文件、未提交内容或分支。

- 本地独有、未上传的文件必须妥善备份保存（仓库外，如 `%USERPROFILE%\.codex\file-backups\`）。
- 执行 `git reset --hard` / `git clean` / 分支删除 / 清理操作前，必须先：
  1. `git status` 检查未提交改动（含已跟踪文件的工作区修改、暂存区内容）；
  2. 找出"本地有但远端没有"的已跟踪文件（`git diff --name-status <本地分支> <origin/xxx>`）；
  3. 将上述文件/改动完整备份到仓库外后才允许继续；未提交改动 reset 后无法恢复。
- 清理 / 删除本地独有文件或分支，必须经过用户特意批准；未经批准一律禁止删除。
- 保持本地与远端一致：版本更新 / 功能完成后及时 push，避免本地与远端长期分叉、脱节；发现分叉先备份再同步。
## 发布检查清单（Checklist）

- [ ] 0. 安全预检：重置/清理前备份本地独有文件与未提交改动；删除须经用户特意批准
- [ ] 1. 功能代码开发完成并自测
      - `npx tsc --noEmit` 无类型错误
      - `npm run build` 构建通过
      - 关键路由手动 / HTTP 验证
- [ ] 2. 撰写当天开发日志 `docs/开发日志[YYYY.M.D-版本].md`
      - 固定五段式：Plan/策划、Coding/关键、Target/目标需求、Questions/瓶颈点、Follow/优化拆解
      - 不包含 emoji，语言简洁，标注新增功能 / 文件的落点
- [ ] 3. 更新开发日志索引 `docs/开发日志.md`，在版本记录表新增一行
- [ ] 4. 撰写版本文档 `docs/versions/版本.md`
      - 结构：更新内容 / 主要新增文件 / 主要修改 / 其他
- [ ] 5. 同步 `README.md`
      - 标题与徽章版本号
      - 项目简介「当前版本」段落
      - 核心功能表（如有新功能）
      - 项目目录树（新增 / 修改文件的落点）
- [ ] 6. 更新 `package.json` 版本号（如 1.2.3 -> 1.2.4）
- [ ] 7. 提交分支：功能代码 + 全部文档同批提交
- [ ] 8. 推送分支并发起 PR，PR 描述附变更清单

## 分支策略

沿用 README「分支策略」：

```
main        ← 稳定发布分支（受保护）
  ├── develop              ← 集成分支
  │   ├── feature/xxx      ← 功能开发
  │   └── fix/xxx          ← Bug 修复
  └── hotfix/xxx           ← 紧急修复
```

版本发布使用版本分支（如 `1.2.4`），紧急补丁使用 `hotfix/xxx`。

## Commit 信息规范

沿用 README「Commit 信息规范」：Conventional Commits 前缀（`feat` / `fix` / `docs` / `refactor` / `perf` / `test` / `chore` 等），描述变更内容。

---

## 说明

- 开发日志、版本文档、README、package.json 版本号四项缺一不可。
- 若因故漏写文档，必须按本清单打热补丁补齐，并重新提交分支 / PR（下不为例）。
- 文档命名规范：
  - 开发日志：`docs/开发日志[YYYY.M.D-版本].md`
  - 版本文档：`docs/versions/版本.md`
