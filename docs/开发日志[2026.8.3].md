## Questions / 瓶颈点

### 前后端分离的技术栈调研（本版本仅分析，不做代码改动）

现状分析：项目当前是 Next.js App Router 单进程全栈结构，服务端能力由三层组成：Server Actions（src/actions/，登录注册、分类、文件、资料）、Route Handlers（src/app/api/，上传分块等）、middleware.ts 路由守卫。数据层为 Prisma + SQLite，认证为自研 Session（httpOnly Cookie，7 天有效期）。前端状态（待办、随手记、音乐盒）目前存 localStorage / IndexedDB，未落入数据库。

向全栈分离演进时，需要考虑的技术栈与问题如下。

一、后端框架选型

- NestJS（Node.js/TypeScript）：与前端同语言，类型可共享；自带模块/依赖注入/守卫体系，与现有 auth 逻辑迁移最平滑；生态成熟、文档完善。缺点是框架较重、学习曲线偏陡，中小型项目略为冗余。
- Fastify（Node.js/TypeScript）：性能高、插件化、轻量，适合纯 REST 服务；配合 fastify-zod 做校验。缺点是脚手架与约定较少，结构需要自行约束。
- Go（Gin / Echo）：高并发、低资源占用、单二进制部署；适合后续多端接入。缺点是与现有 TypeScript 代码不共享类型，需要重写服务端逻辑，团队成本高。
- Java（Spring Boot）：企业级生态，适合事务型业务；缺点是与当前轻量栈差距最大，迁移成本最高。

建议：优先 NestJS 或 Fastify，与现有 TS 技术栈衔接成本最低，可逐步迁移而非重写。

二、数据库升级

- 现状 SQLite 仅适合单机开发与演示，多实例部署、并发写、线上运维均有瓶颈。
- 生产环境建议 PostgreSQL（或国内云厂商 RDS/MySQL），Prisma 已抽象数据层，切换成本主要是方言差异与迁移脚本；需要把现有 dev.db 数据做导出迁移。
- 前端 localStorage/IndexedDB 中的待办、随手记、音乐数据在后端没有对应表，分离后必须新增 Notes / Todos / Music 等数据模型，否则多端同步无从谈起。

三、认证方案

- 现有 Session + Cookie 机制在前后端同域部署时可用，但分离部署（前端 Vercel、后端云服务器）会遇到跨域 Cookie 问题。
- 可选方案一：改为 JWT（Access Token + Refresh Token），前端存内存/localStorage，无状态、跨域友好；缺点是登出与吊销需要额外处理。
- 可选方案二：保留 Session，后端独立管理会话存储（迁移到 Redis），Cookie 设置 SameSite=None + Secure 并处理 CORS 白名单。
- 推荐引入 Auth.js（NextAuth）v5 统一 OAuth（GitHub/微信/邮箱验证码）能力，减少自研代码维护量。

四、文件存储

- 现状文件落盘 public/uploads（按日期目录），分离后前端构建产物与用户文件不应同源托管。
- 建议迁移到对象存储（阿里云 OSS / 腾讯云 COS / S3 兼容存储），后端生成预签名 URL 供上传下载，图片缩略图用 sharp 生成后入存储。
- 大文件分块上传逻辑（src/app/api/upload/chunk）需要改造为直传对象存储或经后端转发，注意分块校验与断点续传的兼容。

五、其他基础设施

- Redis：会话缓存、接口限流（现限流在 lib/security.ts 内存实现，多实例下失效）、热数据缓存。
- 任务队列：BullMQ（缩略图生成、回收站 30 天清理、文件哈希计算的异步化）。
- API 形式：REST（简单直观，配 OpenAPI 文档）或 tRPC（与 TypeScript 端到端类型安全，适合 NestJS/Next.js 组合）；GraphQL 对当前规模偏重，暂不推荐。
- 部署拓扑：前端 Next.js 静态导出或 Node 服务（Vercel / Nginx + PM2），后端独立 Node 服务（Docker + Nginx 反向代理 + HTTPS），数据库与 Redis 托管或自建。

六、迁移注意事项

- 代码分层：先抽出 src/services/ 业务层（目录已存在但为空），把 Server Actions 中的业务逻辑下沉，后续整体搬运到后端。
- 环境变量拆分：前后端各自维护 env，密钥隔离（JWT_SECRET、OSS_KEY 等）。
- 中间件与权限：现有 middleware 仅校验 Cookie 存在性，分离后需在后端接口层做统一鉴权与权限校验。
- 兼容窗口：建议保留 Server Actions 一段时间，双轨运行逐步切换 API，避免一次性大改。

优缺点小结：
- 优点：前后端独立部署、独立扩容；前端可静态托管降低成本；后端可接入多端（Web/App）；测试与运维边界清晰。
- 缺点：架构复杂度上升（CORS、鉴权、部署、监控都需要额外处理）；现有代码需要较大重构；小规模使用场景下单进程 Next.js 已足够，分离是"为了成长"的投资。
- 结论：建议在用户量与功能复杂度上来后再落地，优先做"数据模型补齐 + 服务层抽取"两项准备性工作。

## v1.1.2 补丁：自定义背景壁纸上传清晰度优化

### Plan / 策划

问题背景：
- 后台"更换背景壁纸"上传自定义图片时，原逻辑直接 FileReader 读取原图存入 localStorage，未做任何处理
- 低分辨率图片（如手机截图、压缩小图）被 CSS cover 放大铺满屏幕后明显模糊
- 高分辨率照片 base64 后体积可达数 MB，接近 localStorage 5MB 配额上限，可能保存失败或拖慢性能
- 手机竖拍照片的 EXIF 旋转方向未应用，显示时可能横置

方案决策：
- 新增 `src/lib/wallpaper.ts` 处理工具，上传后用 canvas 智能重绘再入库：
  - 低分图（最长边低于屏幕尺寸或 1600px）等比放大到屏幕级尺寸，开启 imageSmoothingQuality: "high" 高质量重采样，cover 铺满后清晰
  - 超大图（最长边超 2560px）等比压缩，控制 data URL 体积
  - createImageBitmap 的 imageOrientation: "from-image" 自动应用 EXIF 方向，不支持时回退 Image + objectURL
  - 透明图（png/webp/gif）保留 PNG 格式，体积超限回退 JPEG（白底填充）
  - data URL 字符数超 200 万再逐级降采样兜底（localStorage 按 UTF-16 计配额）
- 上传期间显示"正在优化图片…"处理中状态，优化失败自动回退原始图片保证功能可用
- 壁纸存储键与既有数据格式不变（data URL），不影响已保存的壁纸

### Coding / 关键

新增文件：
- `src/lib/wallpaper.ts` — 壁纸图片处理工具：`processWallpaperImage(file)` 解码（EXIF 方向）→ 计算目标尺寸 → canvas 高质量重绘 → PNG/JPEG 智能输出 → 体积兜底降采样

修改文件：
- `src/components/layout/dashboard-layout.tsx` — `handleWallpaperUpload` 改为 async 调用 `processWallpaperImage`；新增 `wallpaperProcessing` 状态；弹窗描述更新；自定义壁纸按钮处理中禁用并显示进度文案；失败回退原图
- `package.json` — 版本号 1.1.1 提升至 1.1.2
